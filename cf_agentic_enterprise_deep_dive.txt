从应用 MCP 化到企业能力化：Claudeforce 深度剖析

# 从“应用 MCP 化”到“企业能力化”

## 通过一个真实案例深度剖析 Claudeforce 架构、背后原理，以及对企业应用智能化演进的关键启示
关键词：Claudeforce、AIforce、Headless 360、Agentforce、Enterprise Semantic Layer、Business Capability、MCP、Hybrid Reasoning、Agent Runtime、Governed Execution

## 摘要

过去两年，企业应用接入大模型的主流做法，是把现有应用 API 封装成 MCP Tool，再把这些 Tool 提供给 Agent。这个模式解决了一个非常重要的问题：AI 如何调用企业系统。
但当企业从“几个 Tool 的 Demo”走向“成百上千个业务能力、多个 Agent、多个核心系统”的规模化阶段时，新的问题出现了：
Agent 怎么知道企业到底有哪些能力？
Agent 怎么理解这些能力真正的业务含义？
Agent 怎么区分“创建续约报价”和“正式续签合同”？
哪些判断应该交给大模型，哪些规则必须由确定性系统执行？
Agent 如何跨多个系统完成长期目标，而不是只完成一次 Tool Call？
企业如何保证权限、审批、规则、事务和审计不被模型“自由发挥”？
Claudeforce / AIforce / Headless 360 所代表的新模式，本质上是在回答这些问题。
它不是简单地把 Salesforce 的 API 再封装一层，而是在推动一种新的企业软件架构：**从 Application-centric 转向 Capability-centric； 从 Tool-enabled Agent 转向 Governed Agentic Enterprise； 从“应用调用 AI”转向“AI 调用企业能力”。**
这篇文章通过一个“保住高风险续约客户 ACME”的案例，逐层拆解这一架构。

这个模式最大的价值是解决了：**Connectivity：AI 怎么调用应用。**
但它没有真正解决：**Business Understanding：AI 怎么理解企业业务。**

# 二、为什么“应用 MCP 化”到一定规模后会遇到天花板

假设用户说：“帮 ACME 准备一下续约。”
企业有四个 Tool：
createQuote()
createContract()
renewContract()
amendContract()
从技术角度，Claude 都可以调用。
但真正的问题是：
用户要的是一个续约报价？
还是合同草案？
还是正式续签？
还是修改原合同？
如果只是靠函数名和 Prompt，Agent 必须自己猜。
再比如用户说：“这个客户风险很高，可以给点优惠。”
Agent又必须理解：
8% 是否允许直接给？
12% 是否需要 VP 审批？
18% 是否要 Finance 审批？
谁拥有最终授权？
这时会发现：**API 能调用，不等于业务能理解；Tool 能执行，不等于企业能治理。**
因此，第一代模式真正的问题不是 MCP 不够强，而是：
AI 有了“手”
但还没有真正理解企业世界。

# 四、Capability 不是 API，也不是一个简单函数

以：
CreateRenewalQuote
为例。
如果它只是：
createRenewalQuote(customerId, discount)
它仍然只是一个 Tool。
真正的 Business Capability 应该描述：
Capability:
CreateRenewalQuote

Business Meaning:
为已有有效合同创建续约商业报价

Source Object:
Active Contract

Target Object:
Draft Renewal Quote

Lifecycle:
Pre-Renewal

Preconditions:
- Contract is active
- Renewal window is open
- Customer is valid
- Pricing is available

Commitment:
Non-binding

Side Effects:
- Create Quote
- Update Renewal Opportunity

Policies:
- Discount <= 10%: manager can approve
- 10% < Discount <= 15%: VP approval
- Discount > 15%: Finance approval

Execution:
Workflow / API / Flow / Service
因此：**Capability = Business Semantic Contract + Executable Contract**
它不仅告诉 Agent：“怎么调用我”
还告诉 Agent：“我是什么、什么时候该用我、什么时候不能用我、调用以后企业世界发生什么变化。”

# 八、具体案例：保住 ACME 的高风险续约

这些属于：**Intelligence / Reasoning**

# 十一、Agent Planning 与 Workflow 的真正区别

用户说：“保住 ACME。”
这是一个 Goal。
可能存在多种路径：
Path A → Service Recovery
Path B → Price Incentive
Path C → Executive Engagement
Path D → Product Migration
Agent 的职责：**从多条合法路径里选择下一步。**
Workflow 的职责：**一旦选定某条路径，保证它被正确执行。**
例如 Agent 选择：
Price Incentive
接下来：
Calculate Price
→ Check Margin
→ Validate Discount
→ Approval
→ Create Quote
这部分应该高度确定。
因此：
Agent = Decide WHAT
Workflow = Execute HOW

越靠近真实交易，越必须确定。

# 二十六、Knowledge、Semantic、Policy 三者必须分开

### Knowledge

例如：“战略客户在重大服务故障后，建议优先安排高层沟通。”
它影响：
Reasoning

### Semantic

例如：
Quote ≠ Contract
Contract has Lifecycle
Quote can become Accepted
它定义：
Business World

### Policy

例如：
Discount > 15%
requires Finance approval
它约束：
Execution
因此：
Knowledge
→ influence reasoning

Semantic
→ define meaning

Policy
→ constrain execution
绝不能混为一体。

# 二十七、Capability 风险分级

## Level 4：Agentic Process

Goal

## Level 5：Agentic Enterprise

Sales Agent

共享：

企业本身变成一个可以被 Agent 理解和操作的运行环境。

# 二十九、Claudeforce 背后真正解决的问题

因此，Claudeforce 并不是单纯解决：“Claude 怎么调用 Salesforce？”
它真正解决的是：

### 1. 能力规模化

企业存在成千上万个 API / Workflow / Action，Agent 如何发现正确能力？

### 2. 业务语义

Agent怎么知道 Quote、Contract、Order、Renewal 的区别？

### 3. 推理与执行边界

哪些应该让 AI 动态判断，哪些必须确定执行？

### 4. 治理复用

权限、审批、Policy、Validation 能否继续沿用原企业系统？

### 5. 多 Agent 共用同一企业能力底座

Claude、Agentforce、Slackbot、自研 Agent 是否可以共同使用同一能力体系？

### 6. 长期任务运行

Agent如何围绕 Goal 保存状态、等待 Event、恢复、重新规划？
这些问题才是从“AI Demo”走向“Agentic Enterprise”的真正门槛。

# 三十、Claudeforce 的几个关键技术和架构创新

## 创新 1：Headless Enterprise

企业应用的价值开始从：
UI + Logic + Data
转向：
Semantic
+
Capability
+
Rule
+
Workflow
+
Transaction
UI 不再是唯一入口。

## 创新 2：Semantic Capability

从：
API Endpoint
升级成：
Business Semantic Contract
+
Executable Contract
Agent消费的不再是底层 API，而是业务能力。

## 创新 3：Discover / Describe / Dispatch

不是把几千个 Tool 全部塞进模型，而是：
动态发现
→ 动态理解
→ 动态执行
形成可扩展的企业能力空间。

## 创新 4：Hybrid Reasoning

不是：
Everything → LLM
而是：
Judgment → LLM
Rule / Workflow / Transaction → Deterministic Runtime
这是企业可靠性的关键。

## 创新 5：Progressive Determinism

越接近 Goal：
自由度越高
越接近 Transaction：
确定性越强
这是比“Agent + Tool”更成熟的企业 Agent 设计哲学。

## 创新 6：Goal-oriented Runtime

软件不再只运行固定 Process。
开始围绕：
Goal
Plan
Task
State
Event
运行。
这使 Agent能处理长周期、多系统、动态变化的业务任务。

# 三十三、最后用一句话理解 Claudeforce

旧模式：**给 Agent 一箱工具，让它自己决定怎么干活。**
Claudeforce 所代表的新模式：**给 Agent 一张企业业务地图和一套受治理的业务能力；允许它自由决定走哪条路，但每条路具体怎么执行，由企业确定性系统保证。**
更进一步：**AI 决定 WHAT / WHY；Enterprise 决定 CAN / HOW。**
这就是从“AI 功能”走向“Agentic Enterprise”的核心架构变化。

# 三十四、企业落地时最值得从哪里开始

不建议一开始就建设全企业 Ontology，也不建议从“超级 Agent”开始。
更现实的第一步是：
1. 选择一个跨 3～5 个系统、需要判断又需要执行的业务场景。
2. 盘点 10～20 个核心 Business Object。
3. 抽象 30～100 个 Business Capability。
4. 建立第一版 Capability Registry。
5. 为高风险 Capability 增加 Policy / Permission / Approval。
6. 复用现有 Workflow 和 API。
7. 建立 Discover / Describe / Execute。
8. 在少数决策点加入 LLM Reasoning。
9. 再逐步引入 Goal / Plan / Task / Event 的 Agent Runtime。
这样企业可以从：
AI Assistant
逐步走向：
Governed Capability
再最终进入：
Agentic Enterprise
而不是一开始就把核心业务交给一个“会调用很多 Tool 的大模型”。
