四个场景共用的一个设计：所有「该不该」的判定都在网关和存量系统里，不在模型里——模型只负责理解意图和填参数。 模型本身也被网关管着：每次模型调用都经模型网关（mock / 回放 / live 三态按请求钉定），调用留痕、按租户计量计费。 令牌逐跳收窄：T1 像工牌（只能聊天）→ T2 像「本会议室门禁卡」（场景∩清单，15 分钟）→ T3 像「操作票」（单工具，60 秒）→ OT 像「一次性的盖章授权书」（绑定参数指纹，用一次作废）。 出问题能精确回答「哪个 Agent 替谁在什么范围干了什么」。接下来两章解释为什么这样设计（01 / 02）。

01这是什么：从一个真实事故讲起Why & What

刚才的动画里，李四的一个提问过了五道关。现在退一步讲：为什么需要这五道关—— 从一个我们真实吃过的亏说起。

先讲一个吃过的亏。 同一份数据、同一个用户，三个入口查出来的结果不一样：财务张三在 ERP 页面上看到 约 50 条发票（系统按他的组织权限做了过滤）；但用系统对外的 Open API 查同一批数据， 返回了 5000 多条——整整 100 倍，因为老接口是十几年前给机器用的，只有「租户级」隔离， 根本不知道「张三只能看华东」这件事。如果今天把 AI 接到这样的接口上，AI 就成了那个 「什么都能看的员工」，而且它的每一次越界，页面上一片安静，没人知道。

这就是企业接 AI 进 ERP 时反复摔跤的四类问题，也是本项目要逐一解决的事：

① 数据权限口径不一致

老接口是机对机设计，只有租户隔离、没有人的权限。AI 接上去 = 拿到万能钥匙。

② Agent 影子接入，无法治理

各个团队自己偷偷接 AI，没有注册、没有吊销、没有审计。出了事查不到「哪个 AI 替谁干了什么」。

③ 答案事后查不清

AI 给了个结论，当时依据什么规则、调了哪个接口、用的哪个版本，一概无法回溯。

④ 一次误写不可逆

模型是概率系统，会有幻觉。让「可能出错的系统」直接改税码、直接付款，风险不可接受。

05架构判断：14 条总纲逐条讲透 + 本仓增补14 + 5 Beliefs

14 条总纲判断（标「总纲」）回答「ERP 的 AI 到底该怎么建」。每一条都按同样三段展开： 问题（这条判断针对什么现实坑）、 为什么（背后的道理和业界依据）、 怎么做（本演示的落地机制 + 代码落点 + 怎么验证）。 13 条已实现并验证；第 4 条分阶段推进（阶段二第一切片已落地）。 与现行架构逐条对照后，本仓增补五条（标「增补」，15–19）与一条总前提，见本章末节。

1总纲AI 要长在 ERP 里，不是挂在旁边 AI-Native，不是 ERP + AI✅ 已实现已验证
问题
常见的做法是在 ERP 页面旁边挂一个 AI 聊天窗，让它自己连数据库干活。这种「外挂式 AI」 自带一套权限（甚至没有权限概念），页面能看的它全能看，页面不能看的它可能更能看； 它干了什么也不进 ERP 的审计。等于招了一个不上门禁、不留记录的编外员工。
为什么
业界（老丁《AI 原生重构 ERP 选型逻辑》）给了一条可检验的判据：差别不在「能不能生成单据」， 而在 AI 执行业务动作时，是否天然复用 ERP 内核的权限、业务校验、风险拦截与审计追溯。 打个比方：外挂 = 人在车外遥控驾驶（自带一套钥匙）；原生 = AI 坐进驾驶室（用原车的钥匙、 踩原车的刹车、录原车的行车记录仪）。「不推倒存量、用独立智能体底座封装对接」是公认的 两条 AI 原生路线之一（底座优先），拓扑上旁挂 ≠ 外挂，判据是管控是否复用。
怎么做
AI 的每一个动作都走完整治理链：令牌（T2/T3）→ BO 合同（boapi-spec/bo-ap.yaml）→ 存量系统原生校验/幂等/审计。全系统不存在第二套权限体系。验证手段就是开头那个事故的复现： 三口径对照证明「AI 看到的 = 页面看到的」。
落点：erp-ai-action/app/auth（令牌链）+ legacy-erp-ap/.../security/PermissionService（权限同源）
验证：scene_1 三口径对照（页面 ~50 / Open API 5054 / BO API 同组织口径 + 披露过滤维度）scene_1
2总纲传统 ERP 继续做确定性执行，这是它的本分 传统 ERP = SoR + 确定性执行✅ 已实现已验证
问题
大模型是概率系统：同样的输入可能有不同输出，偶尔一本正经地胡说。如果让模型直接参与 记账、付款、成本计算这类必须百分之百准确的逻辑，错误率不可接受，而且错了无法解释。
为什么
ERP 的价值恰恰是「账实相符、事务一致、可回溯」——这是确定性系统的长处； 模型的长处是理解意图、组织信息、给出解释。两者要分工，不是互相替代： 模型当「懂业务的接口层」，事务和规则留在确定性系统里。
怎么做
Java 存量域保持三样东西：事务（@Transactional 与变更同事务落库）、 业务幂等（同一业务键重复发起，重放首次结果，不重复执行）、稳定错误码 （AP.MATCH.QTY_MISMATCH 这类语义化编码，评测直接锚定）。 AI 只能经 BO 合同进入，没有旁路。
落点：legacy-erp-ap/.../service/TaxCodeService（幂等落库）+ rules/RuleEngine（规则引擎）
验证：scene_6 幂等重放（同键再发起命中「幂等重放：是」）scene_6
3总纲AI 是 ERP 的内生组件，共享同一套「器官」 AI 是 ERP 内生组成部分✅ 已实现已验证
问题
有人会质疑：你的 AI 是 Python 底座 + Java 存量两套栈，进程都不同，「内生」从何谈起？ 如果说不清，一句「你这不就是外挂嘛」就能把整个方案打回。
为什么
内生 ≠ 进程同体。内生的判据是「共享器官」：AI 与页面共享同一套权限组件、同一个审计、 同一套幂等语义。就像移植的器官——位置是新加的，但血液循环接进了原系统，受同一套免疫监控。 底座优先（独立智能体底座封装对接存量）被业界明确列为 AI 原生的合法路线。
怎么做
三件事做到共享：① BO 工具与页面走同一个 PermissionService （租户/公司/组织三维判定，AI 侧零权限计算）；② 审计五要素贯穿四个服务； ③ 写路径幂等在 Java 不在网关。一致性由 Java 测试 PermissionParityTest 守护。
落点：legacy-erp-ap/.../security/PermissionService.java（★ UI 与 BO 共用，注释里就写着「权限同源是平价保证」）
验证：PermissionParityTest + scene_1 三口径对照scene_1
4总纲本体：先做语义唯一真相源，再做结构引擎（分三步） Ontology = 统一语义模型 + 逻辑核心⚠️ 分阶段（阶段二第一切片已落地）
问题
模型不知道「进货单」在这家租户指采购订单还是收货单；不知道「大额风险」按哪个阈值算； 字段口径、业务规则散落在各处，每个 AI 应用自己理解一遍，口径必然漂移。 同时还有一个更大的许诺要小心：「本体当逻辑核心」——从「解释业务」升级到「生成业务结构」。
为什么
语义必须唯一真相源（一处定义、处处引用），否则每个 Agent 各念各的经。 但「逻辑核心」要诚实分阶段（本仓与总纲的一致表述）： 阶段一=统一语义与校验核心（术语/指标/规则/护栏/能力问题唯一真相源 + 漂移防护）； 阶段二=本体开始驱动结构（哪怕只从增量段生成一个派生字段 API）； 阶段三=本体成为结构生成的源头（表单/权限/流程）。 把阶段一包装成「逻辑核心」会被懂行的人一句戳穿——诚实分阶段反而立得住。
怎么做
阶段一已达成（见判断 5/9 的机制）。阶段二第一切片已落地：本体增量段声明派生字段 unpaid_cny = amount_cny - paid_cny（声明式计算式）→ 构建期生成器产出 derived-fields.json（带语义版本戳）→ Java 侧通用求值引擎 （DerivedFieldService，不含任何字段特定逻辑）暴露为 BO 操作 ap.invoice.getDerivedField。含义：本体改定义、重建，API 能力随之改变， Java 一行不用改。阶段三（表单/权限/流程生成）是愿景，本仓不冒领。
落点：erp-ai-context/domains/ap_invoice.yaml（增量段）+ scripts/gen_derived_fields.py（生成器）+ legacy-erp-ap/.../service/DerivedFieldService.java
验证：scene_11 驱动半场（unpaid_cny=3400.00 含基字段/公式/版本取证；未定义字段被拒 AP.DERIVED_FIELD_NOT_FOUND；版本链 spec 1.2.0 / ap-sem-1.1.0 同步）scene_11
5总纲元数据自动喂养本体，而不是人工抄写 Metadata 是 Ontology 的输入与来源✅ 已实现已验证
问题
如果本体靠人工维护，存量系统改了字段、加了实体，语义文件没人跟着改——AI 拿着 过期的地图办事，而且没人知道地图过期了。手工维护的语义资产必然腐烂。
为什么
存量系统的元数据（有哪些实体、哪些字段、哪些枚举）本身就是「户口本」，应该实时取用 而不是人工誊抄一份。人只该写机器推不出来的东西：业务术语口径（「进货单」指什么）、 维度分组这类业务约定。机器能生成的让机器生成，剩下的交给漂移检测盯着两边不一致。
怎么做
语义文件三段式里的投影段改为实时生成：实体清单/标签/枚举直接读存量 /metadata 接口（effective_projection， 60 秒缓存，不可达时回落冷启动清单）；存量新增实体（如 PurchaseOrderLine）自动出现， 语义文件从未写过它。配套两条新漂移不变式：口径层术语指向的实体必须存在（TERM_TARGET）、 派生字段的基字段必须存在（DERIVED_BASE）——喂养反过来又加强了校验。
落点：erp-ai-context/service/loader.py（effective_projection）+ drift/drift_check.py（不变式）
验证：scene_11 喂养半场（投影段与 /metadata 完全一致、未手写实体自动出现、新不变式计数可见）；漂移检测预埋 2 处全检出scene_11
6总纲多领域 Agent 协同，但必须显式委派、可追责 多领域 Agent + 协同组合✅ 已实现已验证
问题
单域 Agent 答不了跨域问题：应付 Agent 只能说「发票 120 件 vs 收货 100 件，差 20」， 根因（供应商超开还是收货短交）要到采购域对订单量才知道。但让多个 Agent 自由聊天式协商又不可治理——谁授权了谁、责任链在哪，全成一锅粥。
为什么
业务问题天然跨域，协同是刚需；但协同必须像组织里的「授权办事」：委派要有清单、 要留痕、子代理权限要最小。不能像两个陌生人自愿结对就替公司做决定。

7总纲Agent 干活走完整链路，绝不直连数据库 业务执行：Agent → API → 微服务 → 事务✅ 已实现已验证
问题
给 Agent 一个数据库连接让它自由读写，是效率最高的做法，也是最危险的做法： 没有事务、没有幂等、没有审计、没有权限，出错不可回滚、出事不可追溯。
为什么
动作必须走完整治理链：网关鉴权 → BO API（带人的权限）→ 微服务 → 数据库事务。 每一跳都有令牌、有留痕、有追踪。这条链也是「替换执行端」判断（12 条）的物理基础—— 链上的每一跳都可独立替换。
怎么做

8总纲流程预先画好，模型只填空，不自由发挥 流程以预定义为主，不要求自适应✅ 已实现已验证
问题
「让 Agent 自主规划步骤」听起来很智能，实际后果是：路径不可预测、无法回归测试、 出错不可复现。今天能答对的问题，明天模型换个思路就可能答错，而且你无法定位是哪一步变了。
为什么
执行面（改数据、跑流程）要求可预测、可测试、可审计。模型真正擅长且稳定的是两件事： 理解意图（用户想干什么）和填充参数（从自然语言里抽出单号、税码）。 流程编排这种确定性工作，交给确定性代码。
怎么做
LangGraph 图静态装配（每个场景一张图：分类 → 业务节点 → 完成）；模型只按「动作契约」 （CONTRACTS）输出意图枚举与参数，不产出路径。这样 50 条评测用例才能 确定性回归——同样的输入永远走同样的路。 适用边界（重要）：本条约束的是执行面。数据探索类场景（如高风险供应商发现）是另一种 AI 业务形态——模型在分析侧关系数据上自主决定查询路径，靠只读沙箱、证据强制、人在环裁决来约束 而不是靠预定义流程；发散探索的结论经人确认后沉淀回确定性资产。见原则 17（双面架构，增补）与第 07 章决策三。
落点：hub/graphs/（五张场景图）+ hub/sdk/graph.py（装配薄封装）
验证：评测 50/50（工具正确性 1.0、步数 ≤4）建立在流程确定性之上eval
9总纲业务规则：AI 可以理解、必须遵守、绝对不能改 AI 可理解使用规则、不可修改✅ 已实现已验证
问题
用户对 AI 说「跳过收货确认，直接把这张发票标记为已匹配」——模型如果顺从， 规则就名存实亡；如果规则本身能被模型（哪怕经 bug）改写，等于没有规则。 写在文档里「请大家遵守」是执行不下去的。
为什么
规则是业务资产，AI 是执行者不是立法者。护栏要做成机制：进模型之前拦、 拦得有记录、且只能加严不能放松（不然一个配置失误就把护栏拆没了）。
怎么做
① 护栏三层解析（标品→行业→租户）只加严：放松类叠加直接被拒绝； ② 每次运行记录「用了哪层哪个版本的哪条护栏」（解析查看器可查）； ③ 规则经语义工具 semantic.operation.explain 供 AI 理解引用； ④ 全系统不存在任何写规则的模型工具。
落点：harness-assets/{standard,partner,tenant-*}/guardrails + hub/assets/resolver.py（三层解析）

10总纲触发有三条路：人问、事件推、定时跑 Open API / Event / Scheduler✅ 已实现已验证
问题
如果 Agent 只能等人提问，它就永远只是个问答机器人。业务价值更大的形态是： 业务事实发生时自动响应（发票一被阻断就诊断）、例行任务自动执行（每天筛查一遍风险）。
为什么
三类触发对应三类真实业务形态：系统间调用（Open API）、事件响应（Event，低延迟）、 例行运营（Scheduler）。其中事件触发和消息订阅必须共用一套事件目录， 否则会出现「能被触发但查不到」或反之。
怎么做
形态③无头 API（scripts/headless_mcp.py）；形态④事件：存量域幂等写 outbox（ap.invoice.blocked）→ hub 事件线程拉取 → 无头诊断（event-diag 代理 代表执行）→ 通知用户；形态⑤定时：scheduler 线程周期代表 ap-batch 全量筛查， 结果有变化才通知（不打扰原则），钉定确定性模型通道。
落点：legacy-erp-ap/.../event/ + hub/events.py + hub/scheduler.py
验证：scene_7（定时筛查通知 + 行业包）；审计里可见 sched-* / evt-* 无会话执行留痕scene_7
11总纲人的角色重构：从执行者到确认者、例外处理者、监督者 人：执行者 → 确认者 / 例外处理者 / 监督者✅ 已实现已验证
问题
AI 全自动不可信，事事人审又退化回手工。人的角色必须重新定义：哪些事必须人点头、 哪些事人只处理例外、人靠什么监督全局——监督尤其需要数据基础设施，不是喊口号。
为什么
不可逆动作（付款/入账/税码变更）的最终责任在人，必须确认；流程挂起等人的场景要能 无缝恢复；而「监督」要能随时回答四个问题：谁在用、发生了什么、有没有异常、花了多少钱。
怎么做
确认者：审批台三要素（打算做什么/依据/影响）+ 快照（批准人所见内容留证）+ 参数指纹； 例外处理者：interrupt 挂起（检查点落库，挂起期零常驻凭据）→ 审批后唤醒继续； 监督者：审计五要素 + 四问自检（scripts/selfcheck.py，五分钟出报告）+ 成本台账与审计逐笔对账 + 解析查看器。
落点：erp-ai-action/app/approval/ + hub/graphs/taxcode.py（interrupt）+ scripts/selfcheck.py
验证：scene_6 全生命周期 + WorkBuddy 浏览器 E2E 19 项 + 五分钟自检四问全可答写
12总纲先协同存量，终局替换部分执行——治理面为此预埋对冲 Agent 演进：先协同传统，终局替换部分执行✅ 当前协同阶段
问题
如果终局是 Agent 替换掉部分传统执行，那今天围绕 Java 建的这些治理（审批、令牌、审计） 是不是白建了？终局真到来时，是不是全部推倒重来？
为什么
关键在于治理放在哪一层。如果治理逻辑写死在 Java 里，换执行端=全部重写； 如果治理在网关与合同层（BO API 规格），执行端只是「履行合同的一方」—— 换掉它，管控面一行不改。这就是「替换」能安全发生的架构前提。
怎么做
T3 一次性写令牌、审批三要素+快照+参数指纹、幂等键、审计五要素——全部定义在网关与 bo-ap.yaml 合同层，不在 Java 里。本仓验证不了终局（也不该）， 但验证了「终局发生时治理不变」这个前提。现处协同阶段。
落点：boapi-spec/bo-ap.yaml（★ 合同即治理）+ erp-ai-action/app/{auth,approval}
验证：合同层定义的幂等/审批/审计语义在评测中全量断言；详见 令牌设计架构对冲
13总纲产品化：标品内核 + 配置适配，改配置不改代码 标品 core + Metadata/Ontology/配置适配✅ 已实现已验证
问题
每个客户都要定制：阈值不同、术语不同、行业规则不同。如果靠改代码/拉分支满足定制， 版本会爆炸，标品永远收敛不回来。
为什么
SaaS 产品的差异化要放在配置层：标品出标准资产，行业出行业包，租户出个性化覆盖—— 三层叠加、优先级明确、护栏只加严。配置还要有界面、改完即生效，而不是让实施顾问改 YAML 发版。

14总纲SaaS：租户隔离层层成立，扩展走 API 和消息两条道 标品层/租户层隔离，API / Message 扩展✅ 已实现已验证
问题
多租户系统最严重的事故就是数据串租；而租户的定制需求如果只能改核心代码来满足， 标品就被拖垮。租户要能自助接入自己的系统，又不给核心开后门。
为什么
隔离必须在每一层同时成立才有意义：数据（查询互不可见）、语义（口径各答各的）、 消息（投递按租户）、成本（记账按租户）。扩展通道是「不开放核心改造」前提下唯一的 集成方式：API 让租户的程序调进来，Message 让租户的系统接出去。
怎么做
双租演示（华东制造 T-EAST / 星联科技 T-UNI）验证隔离：数据/术语/口径/成本四层互不可见。 API 扩展 = BO API（规格即工具）；Message 扩展 = 租户消息订阅（topic × webhook × HMAC-SHA256 签名），事件按（租户 × topic）隔离投递出平台，逐次审计，吊销即停—— 与形态④同源：同一 outbox 事件，「事件进 Agent」与「事件出平台」不是两套事件。

判断之间的关系：三个需要表态的张力点

14 条不是并列的清单，有几处互相拉扯，需要明确表态（否则会被问倒）：

A · 「内生」（3）vs 两套栈的拓扑

Python 底座 + Java 存量，字面上像「外挂」。表态：内生 = 共享器官（权限/审计/幂等）， 不是进程同体；底座优先是业界承认的原生路线。三口径对照是证据。

B · 「本体是核心」（4）vs 「元数据是来源」（5）

从元数据推导的本体只是镜子——镜子能校验（漂移检测），不能当引擎。表态：分三阶段， 本仓已走到阶段二第一切片（派生字段→API）。把阶段一说成核心会言过其实。

C · 「终局替换」（12）vs 「存量确定性」（2）

替换之后谁做确定性执行？表态：治理面在网关与合同层、不在 Java——执行端只要履行 同一 BO 合同（同幂等语义/同错误码/同审计），管控面零改动。这是替换的对冲。

增补17 · 双面架构：执行面与探索面

14 条总纲描述的都是执行面（替人办事：预定义流程 + BO API + 确定性优先）。 数据探索是另一种 AI 业务形态（替人发现）：湖仓直查（绝不碰交易库）+ 关系图谱 + AI 引导遍历 + 证据链 + 人在环裁决 + 确认后沉淀回执行面。两个面共用语义层与治理， 差异只在数据通道与确定性纪律——原则 7/8 的边界由此划定。 详见第 07 章决策三、第 02 章两张逻辑图。

增补18 · 异构系统对接（MCP 多系统）本仓未做

底座优先路线的三大工程挑战之首（参照文原文点名）：AI 底座要能对接多套异构业务系统 （ERP / OA / CRM），不绑定单一产品——参照文选型第四条明确要求。 本仓现状：MCP 代理只指向一套 Java，诚实标注为路线图项——再挂一个只读 OA/CRM 工具即可演示「底座不绑定单一 ERP」。

增补19 · 知识库建设节奏：场景驱动生长

骨架一次建好（三段式 / 自动喂养 / 漂移检测 / 评测同源绑定），血肉按场景生长 （每寸口径层资产都带评测锚）。「一次建全、一劳永逸」没有消费验证、漂移面积线性增长、 组织上永远差 30% 上不了线——参照文选型第五条「单点切入、拒绝一步到位」正是此意。 详见第 07 章决策四。

07知识库专题：存哪、建多深、怎么长、探索面Semantic KB: Storage · Depth · Rhythm · Exploration

语义知识库（L3a，代码落点 erp-ai-context/）是「让 AI 看得懂 ERP」的那一层。 本章讨论四个最容易吵翻天的问题：存储用什么（YAML 文件还是图数据库——含业界判据与硬指标）、 建到什么深度（把存量业务逻辑搬进来描述一遍，还是只画一张地图）、 按什么节奏建（场景驱动生长，还是一次建全一劳永逸）、以及 探索场景怎么办（数据探索是否还该走 API——一种不同的 AI 业务形态）。 每场争论都摆开双方立场，给出本仓的判断、依据与边界。

决策一 · 存储选型：YAML 文件，还是图数据库（Neo4j 一类）？先摆立场，再给判断标准

先把两种立场的最强论证都摆出来：

立场 A ·「YAML 够用」

领域小、实体少时，语义文件可读、可评审、可 git 版本化、零运维。 汇报时能当场打开文件给评审看全部语义资产；变更走 code review，谁改的、为什么改， 一目了然。图数据库在这个规模是「用生产级复杂度换不存在的能力」。

立场 B ·「必须上图」

真实 ERP 的语义规模远超文件能承载：SAP 知识图谱覆盖 730 万个字段、实体、流程与关系， 且内含权限规则。多跳关系查询（「这张发票的供应商，还关联着哪些被拦的单？」） 在 YAML 里根本没法表达；多域多租户的叠加解析需要索引而不是遍历。

本仓的判断：这不是信仰之争，是规模与查询模式的函数。先回答「业界有没有硬性指标」，再给可测的判断标准。

业界有没有硬性数字门槛？——没有硬门槛，但有可量化的技术判据

诚实的回答：业界不存在「超过多少个实体必须上图」这样的硬性标准——厂商和论文给的是判据方向， 不是数字门槛，而且判据本身存在争论。但有一条技术锚点是硬的，可以拿来做工程决策：

技术锚点 · 遍历成本模型（index-free adjacency）： 原生图数据库（Neo4j 一类）的每个节点直接持有指向相邻关系的指针——每跳一跳是一次 O(1) 的指针追访， 成本只和「实际走过的子图大小」有关，与全图大小无关；关系型数据库每次 JOIN 是一次约 O(log n) 的 索引查找 + 连接开销，成本随表规模和 JOIN 深度累积（出处：Robinson / Webber / Eifrem 《Graph Databases》第二版，O'Reilly；Neo4j 官网提供免费电子版）。 实证区间：Neo4j 公开的「朋友的朋友」基准中，1~2 跳两种引擎性能相当；3~4 跳时关系型急剧劣化、 图数据库近乎平坦——这是「什么时候该上图」最有参考价值的经验分界。
反方意见（诚实引用）：Morales《Index-Free Adjacency? Hybrid Indexes/Adjacency for Graph Databases》（arXiv, 2021）指出 O(1) 宣称有营销成分——B 树索引常数极小、图库定位起点节点仍需索引， 2~3 跳内关系库完全可比。本仓据此取保守读法：不到 3 跳交互级查询，不构成上图的性能理由。

规模端点的参考：SAP 知识图谱覆盖 730 万个字段、实体、流程与关系，内含权限规则（SAP Sapphire 2026， 见总纲第 01 章引注）；本演示 8 个实体、约百个字段——两端相差六个数量级，中间地带靠下面的判据表定位。

决策二 · 构建深度：把业务逻辑搬进来，还是只画地图？这是知识库最容易做错的一个决定

深度问题有两种极端主张。深度 A（搬逻辑）：把存量 ERP 服务的业务逻辑在知识库里描述一遍—— 每条校验规则怎么算、每个流程怎么流转、每个金额怎么记，让 AI「完全理解」业务。 深度 B（画地图）：只描述有哪些业务对象、对象之间什么关系、怎么访问，业务逻辑留在存量系统执行。

本仓的判断：深度 B，且这是四个硬理由支撑的强判断，不是折中：

理由一 · 第二真相源必然腐烂

逻辑写两遍（Java 一遍、知识库一遍）必然漂移。判断 5 的教训已经证明：连实体清单这种 机器可读的东西手工维护都会腐烂，何况业务逻辑——它散在代码里，没有机器可读的接口可喂 （实体能从 /metadata 自动拉，逻辑拉不出来）。搬逻辑 = 纯手工逆向工程 + 永久的双写负担。

理由二 · 执行权不能让渡

规则必须在确定性系统里执行（判断 2/9）。知识库里的规则描述越「可执行」， 越给模型留下自行解释的空间——模型读着知识库说「按规则这张发票应该能过」， 就是幻觉的温床。正确分工：模型引用规则（explain 返回语义），Java执行规则 （RuleEngine 真跑）。

理由三 · 维护成本不可行

一个 AP 模块的规则就够逆向工程几个月，十几个子产品不可行。而对象/关系/字段的元数据 存量系统本来就有（/metadata 免费提供）——地图可以自动画，逻辑只能人抄。

理由四 · 审计要求唯一事实

如果 AI 的结论可以来自知识库里的逻辑描述而非真系统的执行结果，「依据是什么」就有了两个答案。 本仓的应答里每个发现都锚定真实执行取证（工具返回 + 规则码 + 版本戳）—— 结论必须出自真跑，不能出自转述。

但「画地图」不等于浅尝辄止——地图要画到什么颗粒度？本仓的三段式语义文件就是深度的答案， 每一段精确回答一类问题：

决策四 · 建设节奏：场景驱动生长，还是一次建全？「大而全知识库」是一个诱人但危险的主张

策略 A · 场景驱动（先搭框架，随场景生长）

先把容器建好（三段式结构、喂养管道、漂移检测、三层叠加），内容从第一个场景起步—— 每上一个场景补一寸口径层（术语 / 关系 / 指标），每一寸都有评测锚。

策略 B · 一次建全（大而全，一劳永逸）

立项阶段就试图覆盖所有业务域的知识，建成后「所有未来场景都搞定」。 诱惑在于不用反复动知识库；风险在于建成之前它一直在腐烂。

本仓的判断：策略 A，且是强判断。四个理由：

理由一 · 没有消费验证的知识是负债

知识切片的价值在被使用时才成立。大而全建出来的切片没有场景消费、没有评测锚定，错了发现不了。 本仓的机制是能力问题清单与评测用例同源绑定（verified_by）—— 知识长一寸就有一寸的验证；没有场景的切片连验证的资格都没有。

理由二 · 漂移面积与维护成本线性增长

手工维护的部分越大，跟不住存量的面积越大（判断 5 的教训：连实体清单手工维护都会腐烂）。 一次建全 = 一次性背上全部域的同步负担，而此时大多数域还没有消费场景来证明这份负担值得。

理由三 · 组织失败模式

「大而全知识库」是典型的长周期基座项目：永远差 30% 上不了线；业务专家被抽调建库， 场景交付反而停滞；最后变成一个昂贵的、还没上线就过期的数据资产。业界对这类项目的结局并不陌生。

理由四 · 自动喂养让增量几乎免费

框架建好后，基础层（实体 / 字段 / 枚举）由 /metadata 实时生成——不花钱； 场景只需要补「口径层」（机器推不出的术语、关系、指标定义）——增量成本极低。 既然增量便宜，就没有必要为省增量而预建全量。

一句话：骨架一次建好，血肉按场景生长。「骨架」= 三段式结构 + 自动喂养管道 + 漂移检测 + 三层叠加 + 评测同源绑定——平台资产，一次建好所有场景共用； 「血肉」= 各场景的口径层资产——按场景生长、带评测锚、错了能发现。 业界参照：SAP 730 万项知识图谱也不是一次建成的——它是数十年产品元数据的持续沉淀， 但它的「骨架」（图谱 schema、喂养管道、权限内嵌）是平台化的一次性投资。 本仓走的就是这条路：ap_invoice.yaml 从单场景长起（诊断 → 筛查 → 税码 → 跨域 → 派生字段）， 每长一寸都有对应的 scene 与评测断言。

决策三 · 探索面：不是所有场景都该走 API「流程画在图里」的适用边界，与另一种 AI 业务形态

一个会打破前面结论的问题。 「探索 P2P 流程里的高风险供应商」——这不是「INV-A-001 为什么被拦」（单点、有明确答案、路径已知）， 而是「沿着数据找异常」（开放、发散、路径未知）。前者是执行，后者是探索。 对探索类问题，预定义流程图 + BO API 这套打法会遇到三个真实困难：

困难一 · BO API 不够用

执行面 API 是按「已知高频操作」设计的（查校验、查差异、改税码）。 「高风险供应商」要先聚合发票-订单-收货-付款多维数据、再按多种风险模式扫描—— 没有为这种开放查询预建 API，逐个建也不现实。

困难二 · 路径没法预先画

探索的价值恰恰在不知道该问什么：先看供应商集中度，发现异常再下钻对账差异， 再追关联收货组织——每一步取决于上一步发现了什么。预定义图表达不了「走着瞧」。

困难三 · 确定性不是目标

执行面要的是每一步可预测、可回归；探索面要的是发散与创造力—— 多查几条路径、多提几个假设，本来就是这类工作的价值所在。用执行面的纪律约束探索，探索就死了。

所以答案是：是的，这是一种不同的 AI 业务场景，需要一套不同的策略。本仓把它表述为 「双面架构」——AI 在两个面上扮演不同角色、用不同打法、受不同约束：

执行面（本仓已建）探索面（本仓未建，本节给出设计）
AI 的角色操作员：替人执行已知操作分析师：替人发现未知模式
数据访问只经 BO API（带人的权限、幂等、审计）分析侧数据湖/湖仓直查（绝不直连交易库），行列级权限在湖上强制
流程预定义场景图，模型只填空（判断 8）关系图 + AI 引导遍历：模型决定下一步查什么，在关系上走
确定性要求每步可预测、可回归、可幂等允许发散与假设——幻觉只允许出现在假设阶段，不允许出现在结论阶段
人的位置不可逆动作的审批人发现的最终裁判：AI 的输出在确认前只是假设
结果形态落库的变更 + 审计证据包（查询语句 + 数据快照 + 推理路径），人确认后沉淀

探索面的四条设计纪律（发散不等于失控，约束换了个地方）：

① 只读 + 分析侧基础设施

探索面在数据湖/湖仓上运行（ELT 从交易侧单向同步，延迟分钟级可接受）， 物理上不碰交易库——探索再重的查询也影响不到付款入账。这和分析侧做数据报表是同一套基础设施与同一套原则， 只是消费方从人换成了 AI + 人。

② AI 不拿裸表权限：语义层中转

AI 不直接写 SQL 扫湖，而是经语义层/图谱生成受约束的查询（查询计划白名单：只读、资源上限、行数上限）； 术语口径沿用同一套知识库（「高风险」在这个租户怎么定义，探索与执行必须是同一个答案）。 6.1 节的图数据库判据在探索场景下全面倒向图——多跳关系遍历正是图的用武之地。

③ 证据优先于结论

每条探索发现必须携带可复现的证据链：查询语句、数据快照、推理路径。这一条是对冲探索面更高幻觉风险的关键—— 结论可以错，但证据必须真、可重放。拿不出证据的「发现」直接丢弃，不进入确认环节。

④ 人确认后固化闭环

AI 发现「某供应商高风险」→ 证据包给人 → 人确认成立 → 沉淀为确定性资产： 定期筛查指标、一条护栏、甚至一个新的 BO 能力。探索面成为执行面的雷达—— 发散的探索负责发现，确定性的系统负责固化，探索的创造力最终回流到可治理的轨道上。

对判断 8 的修正（重要）：「流程以预定义为主」的完整表述应该是——执行面流程以预定义为主， 模型只填空；探索面允许模型自主决定查询路径，代价是：只读沙箱、证据强制、人在环裁决、结论沉淀闭环。 两个面共用同一套语义层与同一套身份/审计，差异只在访问通道（API vs 湖查询）与确定性纪律的松紧。 这与第 01 章 L0 分层完全兼容：探索面 = L3a 语义（图谱）+ L4 能力组件（数据湖/检索）的组合应用， 业界「Agentic Analytics」正是这个方向。本仓未建探索面，它是路线图上的下一块—— 但它的治理要素（语义同源、证据链、人在环、审计）本仓全部已有，缺的只是数据湖一侧的接入。

一、应付（AP）产品的工作项本仓 legacy-erp-ap 的真实清单 —— 每项配可运行示例

AP 产品在 AI 架构里的任务不是「接入 AI」，而是把自己的业务能力以带治理的合同形式暴露出来。 八个工作项，按依赖顺序：

AP-1定义 BO API 规格（全项目唯一规格真源）boapi-spec/bo-ap.yaml

做什么：AP 提供一个通用的「字段计算器」，但不写死任何具体计算——算什么、怎么算， 全部来自语义层（本体）的定义文件。打个比方：AP 交付的是 Excel 程序本身，公式写在表格里—— 改公式不用重装 Excel。

举个例子：财务想要一个新指标「未付金额」（发票金额减已付金额）——

AP 明确不做的事：不建权限体系（复用组件与平台令牌）、不建网关与模型通道、不建语义服务、 不写 Agent 编排（hub 是平台/应用层的）、不建评测框架。判断口径：换一个产品（应收、库存）， 这些工作项的「内容」全变、「结构」不变——每个产品都有一份自己的 bo-spec、PermissionService、outbox、/metadata。

二、ERP 应用层的共享能力每个产品都要用、但谁都不该私设的部分 —— 本仓已逐项落地

平台不管业务、单个产品管不了全局——中间有一层「跨产品约定」，归 ERP 应用层。 这层的判断口径：一旦某个产品私设，跨域协同和口径一致性就断了。七个工作项：

ERP-1事件目录与契约治理契约：outbox event_type + payload 约定

「发票被阻断」这个事件叫什么名、载荷里有什么字段、谁可以订阅——必须全 ERP 一份目录。 事件的 L1 触发入口与 L3 Agent 感知通道共用同一套目录，否则出现「能被触发但查不到」。

# 事件契约（AP 发布的例子；目录归应用层统管） event_type: ap.invoice.blocked # 命名约定：{产品}.{对象}.{事实} payload: { tenantId, orgId, invoiceNo, amountCny, findings[] } # 载荷字段约定 消费方: 平台事件线程（形态④）· 租户订阅（topic=ap.invoice.*） # 双路同源
验证：scene_7 + scene_9（同一事件双路消费，载荷一致）
ERP-2统一数据权限模型（维度规范）契约：scope JSON 维度约定

每个产品各自实现 PermissionService，但维度模型必须统一（租户/公司/组织三维、all_orgs 语义、 越界按未找到的约定）——否则跨产品 Agent 的权限语义各说各话。模型归应用层，实现归各产品。

# 权限 scope 的统一约定（role_permission.scope_json）—— 应用层定规范，各产品照实现 { "orgs": ["ORG-EAST-PROC"] } # 组织集合 { "all_orgs": true } # 全域（合并规则：任一 all_orgs 即全域） # 约定：越界一律按“未找到”返回（不泄露存在性）—— 全产品一致
验证：PermissionParityTest；scene_1 三口径
ERP-3SoD 互斥与协作清单 —— 谁能用什么、谁能委托谁erp-ai-action/app/db.py（注册表种子：规则内容在这，注册机制在平台）

两条跨产品的治理规则，各举个例子：

① SoD 互斥（申请与审批必须分家）：如果一个 Agent 同时能「申请付款」和「审批付款」， 等于自己申请自己批——所以这两个工具分属不同互斥组，同一 Agent 不能同时持有， 注册时网关直接拒绝（GW.SOD_CONFLICT）。这不是 AP 一家的规则：采购、费用都有同样的申请/审批分家， 是全 ERP 的职责分离原则。

② 协作清单（谁能委托谁）：应付 Agent 查发票数量差异，根因要到采购域取证——它能委托采购 Agent 吗？看清单：

# 应付 Agent 的注册种子：delegates_to 声明它可委托谁 ("ap-copilot", "应付 Copilot", "T-EAST", _READ_TOOLS + _TAX_TOOLS + _SEMANTIC_TOOLS, "lisi", ["proc-copilot"]) # ← 只能委托采购域，别的都 403 # 网关第七道校验的实际效果： ap-copilot 委托 proc-copilot → 放行（在清单内） ap-copilot 委托 rogue-agent → 403（清单外，GW.DELEGATION_NOT_ALLOWED） proc-copilot 反向委托 ap-copilot → 403（不在它的清单里） 跨租户委托 → 403（租户校验另拦）

为什么归应用层：注册中心是平台建的，但「谁和谁互斥、谁信任谁」是跨产品的治理决策—— 如果 AP 私设「我可以委托任何人」，跨域协同的信任链就断了。

验证：scene_3（SoD 注册被拒）+ scene_8（清单外 / 反向 / 跨租委派全部 403）
ERP-4跨产品语义口径 —— 同一个词，谁说了算erp-ai-context（三段式规范 + 租户术语映射）

问题是什么：同一个业务词，在不同租户、不同产品嘴里可能指不同的东西。

举个例子：「进货单」这个词——

# 华东制造（制造业）的财务说「进货单」：先有订单才有货 → 指采购订单 PO 「进货单」—T-EAST 语境→ PurchaseOrder # 问「本月进货单」→ 查 PO # 星联科技（贸易）的仓库说「进货单」：货到才算进货 → 指收货单 GR 「进货单」—T-UNI 语境→ GoodsReceipt # 同一个问题 → 查 GR，答案不同 # 同一句话两家租户两个答案——靠术语按租户映射，而不是两套知识库

「仲裁」指什么：各产品、各租户的术语各自维护（AP 管 AP 的术语），但两件事必须统一约定： ① 三段式结构规范——什么放投影段（/metadata 自动生成，人不写）、什么放增量段（人只写机器推不出的 口径，比如上面的术语映射）、什么放原生段（引用 BO 规格），全 ERP 一套结构；② 冲突仲裁规则—— 当采购产品和应付产品对同一个词（比如「大额」）各自登记了定义且互相打架时，谁定对错、按什么优先级—— 需要一个跨产品的口径治理角色，而不是谁嗓门大听谁的。

为什么归应用层：任何一个产品私改结构或私设口径，跨产品的术语翻译和指标对比就失去了共同语言。

验证：scene_5（双租同题不同答：进货单 / 大额阈值）+ scene_11（三段式喂养与漂移检测）
ERP-5规格扩展标准（x-bo-extensions 约定）boapi-spec/bo-ap.yaml（扩展头注释）

每个产品的 BO 规格用什么扩展标记、版本四件套怎么演进、什么变更导致录制作废——统一约定。 没有这个标准，跨产品的工具治理（网关拦截、审计分类、评测锚定）就无法统一实现。

# x-bo-extensions 统一约定（应用层定，各产品规格必须遵守） x-bo-operation-kind : read | write # 操作性质，入审计与 trace x-bo-irreversible : true 则网关强制审批 x-bo-idempotency : 业务幂等键定义与冲突语义 x-bo-permissions : Java 侧要求的权限码（AI 侧零权限计算） x-bo-completeness : 结果完整性披露契约 x-bo-error-codes : 错误码（六类 category） x-bo-sod-group : SoD 互斥组
验证：网关 tool_registry、gen_manifest、评测 runner 全部按此解析（三处同一份）
ERP-6评测锚点绑定 —— 「能答什么」与「怎么验证」必须是同一份questions-capability.yaml × eval/cases（verified_by 绑定）

问题是什么：系统里有两份清单——给业务看的能力清单（AI 能答什么问题，本仓 30 条）和 给工程师看的评测用例（用什么输入验证什么输出，本仓 50 条）。两份清单不绑定，必然脱节。

举个例子：能力清单里有一条「AI 能解释发票为什么被阻断」——

# 能力清单（给业务看的承诺）——erp-ai-context/questions-capability.yaml - id: q-ap-diag-001 question: "INV-A-001 为什么被阻断？" verified_by: [AP-DIAG-001] # ← 绑定：这道题由哪条用例担保 # 评测用例（给工程师看的验证）——eval/cases/ap-diag.yaml - id: AP-DIAG-001 expect: answer_contains: ["AP.MATCH.QTY_MISMATCH", "AP.BUDGET.EXCEEDED"] # ↑ 必须答出两个真实根因（数量差异 + 预算超支），少一个就不算能答 # 负例成对约定（写路径锚点长这样）——eval/cases/ap-tool.yaml - id: AP-TOOL-008 expect: tool_errors: { ap.invoice.applyTaxCode: GW.APPROVAL_REQUIRED } # ↑ 断言「必须挂起等审批」而不是直接落库——防的是忘了拦，不只是忘了做

如果没有绑定会发生什么：能力清单吹「能答 100 个问题」，评测只覆盖 30 个——剩下 70 个没人验证， 哪天悄悄坏了也没人知道，能力清单沦为营销材料；反过来，评测里有用例但清单没登记，业务根本不知道这个能力存在。

为什么归应用层：每个产品都有自己的能力清单和评测（AP 有 AP 的 50 条），但「怎么绑定、 负例必须成对、六类划分（含幻觉与诱导两个负向类）」是统一规范——否则各产品质量口径不一， 跨产品的质量门禁无从谈起。

验证：run_eval --tier full 50/50 全绿；能力清单 30 条全部有 verified_by 锚点
ERP-7审批分级策略（什么算不可逆）契约：irreversible 判定规范 + 审批三要素约定

税码变更算不可逆吗？批量过账算吗？「不可逆」的判定标准与审批卡的要素（做什么/依据/影响 + 快照 + 参数指纹） 是跨产品一致的约定——归应用层。各产品在规格里打标，网关统一执行。

验证：scene_6（三要素 + 快照 + OT）；scene_3（诱导绕审批被拦，零工具调用）
这一层的组织含义：应用层工作项的产出物大多是约定与治理决策（目录、规范、清单、仲裁规则）， 而不是代码——代码落点在平台（注册机制）或产品（实现）。所以它需要的是一个跨产品的治理角色 （本仓由架构组承担），而不是一个新的开发团队。七个工作项全部有可运行验证，见各模块底部。
