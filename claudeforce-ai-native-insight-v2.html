摘要

企业应用进入AI Native阶段后，难点已经不再是让模型“连上系统”，而是让它理解用户要完成的业务任务，获得实时且可信的企业上下文，找到正确的业务能力，并在现有身份、权限和规则下安全执行。

Claudeforce是Salesforce与Anthropic的联合产品体验；首个具体产品是Claude中的专用插件Salesforce in Claude。它把Sales Skills、Setup Skill、Salesforce与Slack Connector、Claude/Cowork任务环境、用户确认和Salesforce写回组合在一起。

核心判断：Claudeforce并非把CRM数据搬进聊天框，而是把Claude的开放式认知能力与Salesforce的确定性企业能力，组织成从目标委派到受治理执行的工作闭环。
ClaudeforceSalesforce × Anthropic联合产品体系与体验。
Salesforce in Claude用户实际安装和使用的Claude专用插件。
AIforceSalesforce的Live Interface Layer，不是运行时服务器。
Headless Toolkit支撑AIforce的MCP、API、Skills、Plugins和开发工具集合。
Headless 360 MCP Server具体的Salesforce Hosted MCP服务；用四个工具连接持续增长的operations。
Salesforce operation可被Discover、Describe和Dispatch的后端行动单元，不是另一个MCP工具。

01 · WHY

为什么已有MCP，Salesforce和Anthropic仍要亲自下场

因为“模型可以调用Salesforce”只完成了技术连通。一个可规模部署的企业AI Native产品，还必须同时解决任务方法、企业上下文、能力选择、身份治理和端到端体验；这些问题跨越Claude与Salesforce两侧，单靠客户拼接很难稳定解决。

先把出发点说清：MCP解决的是协议，不是完整产品

在Claudeforce之前，客户已经可以让支持MCP的Claude连接Salesforce Hosted MCP Server。连接成功以后，Claude确实能够看到工具、发起调用并获得数据。但这只证明两端“能说话”，并不保证Claude知道应该完成什么销售任务、需要哪些事实、哪个字段代表企业真正使用的指标，也不保证一次查询能够自然推进到交付成果和安全写回。

有连接MCP建立标准调用通道
缺任务方法不知道高质量任务应怎样完成
缺正确上下文不知道当前任务该取哪些事实与语义
缺规模化能力选择大量API和工具难以被模型稳定使用
缺产品闭环查询、分析、确认和写回彼此割裂

客户自己接MCP，真正需要补的是一层“产品工程”

表面上已经有实际仍要由客户解决容易出现的结果
Claude与Salesforce连接把销售目标翻译成稳定的任务步骤、检查项与输出标准回答看似合理，但遗漏关键销售判断
Salesforce对象和记录决定当前任务所需对象、字段、关系、时间范围与协作信息把“数据很多”误当成“上下文正确”
API或MCP工具维护工具名称、参数、权限、版本与Prompt之间的映射工具选择错误、参数猜测和接口幻觉
Salesforce权限体系建立客户端准入、用户身份绑定、写操作确认和异常处理另造一套权限映射，或把模型确认误当成系统授权
聊天界面把研究、分析、Artifact、跨系统协作和CRM写回连成一项工作只能问答，仍需员工手工完成最后一公里
一次可用Demo处理安装、初始化、失败恢复、审计、评估和版本回归试点有亮点，规模部署后质量漂移且责任不清

为什么双方联合产品化更有结构性优势

Anthropic掌握“开放式认知与工作环境”

  • 理解自然语言目标并处理不完整要求
  • 把目标分解为多步骤计划并动态调整
  • 跨Connector综合信息、生成文档与Artifact
  • 在Claude Chat和Cowork中承载连续的人机协作

Salesforce掌握“确定性企业知识与行动”

  • Customer 360中的权威记录、对象关系和应用语义
  • Org元数据、流程、API、Flow、Apex与业务规则
  • 用户身份、CRUD、FLS、Sharing、审批和审计
  • 销售任务知识，以及平台能力如何被安全调用

Claude一侧无法凭模型参数知道某个Org里的自定义字段、销售阶段、共享范围和实时活动；Salesforce一侧也不等同于一个能够理解开放目标、跨系统研究并生成成果的通用工作环境。因此，双方的结合点不是简单“模型＋数据库”，而是开放式判断与确定性企业能力之间的产品契约。

本文用于评价企业AI产品的六项标准

1. 任务可委派用户表达业务目标，而非逐个指定页面、字段和API。
2. 方法可复用系统具备完成专业任务的步骤、检查项和输出结构。
3. 上下文可信且按需实时事实、元数据与语义围绕任务披露，不预载整个Org。
4. 能力可发现和理解模型能够找到正确行动，并在执行前获得明确技术契约。
5. 行动继承原生治理AI代表当前用户行动，权限、规则、确认和审计都可验证。
6. 体验形成闭环从目标、分析、成果、预览到系统写回在同一任务中完成。
WHY的结论Claudeforce要解决的不是“再做一个连接器”，而是把协议、模型、任务知识、实时企业上下文和受治理行动共同封装成一个员工可以直接使用、企业可以持续运营的AI Native产品。

Salesforce升级AIforce后的官方架构口径

Salesforce将AIforce定义为Live Interface Layer：它把Data 360的可信统一上下文、Customer 360的应用与语义智能，以及Agentforce的数字劳动力带到任何AI工作界面。它不是一个新的协议或运行时网关。

AIforce · Live Interface Layer通过Claudeforce、Slackforce、Agentforce Coworker及伙伴产品，把可信上下文与行动带到具体AI工作界面。
Agentforce面向企业的数字劳动力、现成Agent与Agent构建能力；并非每次Claudeforce请求的必经节点。
Customer 360数据对象、业务逻辑、流程、权限、操作与应用语义。
Data 360统一、联邦化的数据、元数据与记忆；按场景参与，不是每次请求的固定路径。

官方命名：Salesforce说明Headless 360已于2026年9月更名为AIforce，但具体Beta服务器仍沿用Headless 360 MCP Server名称。Headless Toolkit是支撑AIforce的技术集合，包括MCP Servers、APIs、Skills、Plugins和Developer Tools。

04 · ENTERPRISE CONTEXT

企业上下文如何暴露：进入模型、成为工具、留在服务端

企业上下文不是一个一次性传给Claude的“Org知识包”。它由任务方法、实时业务事实、元数据与业务语义、能力契约和治理约束组成，并通过三种不同方式参与一次任务。

进入Claude工作上下文用户目标、Sales Skill、相关业务事实、按需取得的结构信息、operation技术契约，以及Slack等Connector结果。Claude据此规划、推理和生成成果。
←
作为运行时可调用能力Salesforce Connector、Headless 360 MCP Server、Salesforce operations，以及背后的API、Flow、Apex和其他平台能力。它们不会全部展开在Prompt中。
←
留在Salesforce服务端强制执行OAuth身份、CRUD、FLS、Sharing、Profile、Permission Set、Validation、自动化、审批和审计。Claude可以知道结果，但不能取代这些控制。

五类上下文分别由谁提供、何时暴露

上下文层具体内容暴露方式与时机作用
任务上下文用户目标、当前对话、交付形式、角色与book of business用户输入；首次使用时由Setup Skill建立个性化界定“这次要完成什么”
任务方法上下文步骤、检查项、所需证据、判断维度和输出结构匹配相关Sales Skill时进入Claude工作上下文界定“应该怎样做”
业务事实上下文Account、Opportunity、Contact、Activity等当前记录及Slack协作信息通过相应Connector及其只读工具或Salesforce operation按任务返回回答“企业现在发生了什么”
元数据与业务语义对象、字段、类型、关系、Picklist，以及阶段、指标和自定义字段在该企业中的含义相关Schema或平台能力按需取得；对象/字段描述、管理员指导和Skill补充模型可见语义回答“数据怎样解释”
能力上下文可用operations及其API、参数、依赖和有序步骤Discover与Describe在需要时渐进披露回答“系统能做什么、怎样正确调用”
治理上下文身份、权限、共享、校验、自动化、审批和审计每次访问与执行时由Salesforce服务端强制实施决定“当前用户实际允许看什么、做什么”

Org元数据什么时候给Claude

连接时：不传完整Org

建立插件、Connector、MCP工具和OAuth会话。公开资料没有表明完整对象模型会在登录时复制给Claude。

规划和读取时：任务相关部分按需取得

Salesforce公开的Operation发现和Schema能力支持按任务渐进取得相关部分；Salesforce in Claude内部如何组合、缓存或预取这些信息尚未公开。

执行时：更多规则留在平台内部

Salesforce可使用未进入模型上下文的元数据、共享规则、校验、Flow和Apex来判断和执行。

结构不等于语义：Schema可以告诉Claude字段名称、类型和关系，却不会自动告诉它“本企业Pipeline Coverage使用Amount还是ACV”“红色风险怎样定义”。完整业务语义还依赖对象/字段描述、管理员指导、指标口径和任务方法。Flow、Validation、Apex与审批主要在服务端强制执行企业规则，除非其说明通过专门能力明确暴露。

权限映射的准确说法

Claudeforce没有把Salesforce权限复制成Claude中的另一套角色表。管理员先用External Client App与mcp_api Scope控制客户端和用户准入；每个用户再用自己的Salesforce账号完成OAuth。此后每次Hosted MCP调用都以该用户身份运行，继续应用CRUD、FLS、Sharing、Profile和Permission Set。Claude侧的“Allow once / Always allow / Deny”是对本次工具行动的产品确认，不能赋予用户原本没有的Salesforce权限。标准Hosted MCP工具由平台实施这些控制；自定义Apex、Flow和REST工具仍需验证运行上下文、sharing、CRUD/FLS检查与错误处理，不能仅因经过MCP就假定天然安全。

05 · HOW

从意图到执行：Operation如何把企业上下文和行动连接起来

用“准备Acme客户会前简报，确认后更新Next Step”这个小案例，可以同时看清Sales Skill怎样提供任务方法、企业上下文怎样进入Claude、Operation怎样被发现和定义，以及读写操作如何继承Salesforce治理。

先用六步读懂业务主链

用户目标委派完整任务
›
Sales Skill提供任务方法
›
Claude规划确定事实与行动
›
Operation发现、核实与读取
›
生成成果事实与判断分开
›
批准写回平台治理执行

下面的正式时序图只是把这六步展开：Discover和Describe属于按需能力发现，紫色框表示进入Claude的上下文，黄色框表示留在Salesforce服务端的治理。

先理解Operation：它位于MCP工具与Salesforce执行层之间

Headless 360没有把Salesforce的成千上万项能力逐个暴露成MCP工具，而是固定提供四个工具，并在后端维护持续增长的Salesforce operations。Operation是一个可被发现、描述和执行的Salesforce行动单元；它把模型的业务意图连接到具体API、参数、依赖和有序步骤。它不是第五个MCP工具，也不是对单个REST API的简单改名。

MCP Server连接入口Headless 360是Salesforce托管的具体Beta服务，提供单一连接。
MCP Tool稳定工具面Discover、Describe、Dispatch和Dispatch Read-Only四个通用工具。
Salesforce operation可扩展行动单元后端持续增长的业务与平台能力，由Discover在运行时检索。
Operation技术契约Describe返回选定行动的API、参数、依赖和有序步骤，供Claude执行前核实。
Access GuardDispatch执行前Dispatch路由到正确端点，并在任何行动运行前实施访问保护。
Sales Skill任务方法告诉Claude销售任务应检查什么、怎样组织输出，不是服务器Operation。
Connector / MCP ClientClaude侧通道管理连接和OAuth会话，把Claude的工具请求发送到Hosted MCP Server。
原生平台治理System of RecordSalesforce继续执行权限、共享、校验、自动化、事务和审计。
四个工具输入/返回的关键含义在案例中的用途
Discover根据Agent对任务的解释，对可用operations做语义检索并返回排序候选找到读取客户近期活动和商机记录的相关行动；风险由Claude根据返回事实和Skill方法判断
Describe返回选定operation的完整技术契约：API、参数、依赖和有序步骤核实候选是否适用，并知道Account标识、时间范围等参数
Dispatch Read-Only调用选定operation，但保证不改变数据或配置读取权限范围内的Account、Opportunity与Activity结果
Dispatch路由到正确端点，在运行前执行Access Guard，再调用选定operation用户批准后，使用已确定并核实契约的写Operation更新Next Step；若尚未确定，应先Discover/Describe

先区分案例中的三类输出

Salesforce业务事实

近期Activity、开放Opportunity、阶段、金额与Next Step等权限范围内的结构化记录。

Claude分析判断

风险信号、优先级、会议议题和建议；它们是基于事实与Skill方法形成的推断。

待批准的执行动作

拟更新的Next Step等变更。只有用户确认后才通过写Operation提交给Salesforce。

案例时序图：每一步暴露了什么、由谁负责

蓝色实线 请求或执行灰色虚线 返回结果紫色框 进入Claude的上下文黄色框 留在Salesforce服务端的治理

从这条时序可以得到四个关键判断

判断案例中的证据边界
企业上下文是运行时组装的任务方法、Operation契约和业务事实分阶段进入Claude不存在登录时把完整Org一次性灌入模型的公开证据
Discover与Describe是渐进披露只有需要查找或核实能力时才进入opt分支预置Skill可能已缩小范围，不能断言每次都严格执行同一序列
Operation契约与Org Schema不同Describe解释行动所需API、参数、依赖和步骤对象字段结构仍需相关Schema或平台能力按需取得
用户确认与平台授权是两道控制Claude先展示拟写入内容；Salesforce仍按当前用户权限和规则执行Allow once不会扩大Salesforce权限，平台失败必须原样返回
术语统一：本文用Sales Skills表示插件中的任务方法，用Salesforce operations表示Headless 360后端可发现和执行的行动单元，用Operation技术契约表示Describe返回的规格。“Operation Library”可以作为普通描述理解为持续增长的operations集合，但不是另一个独立产品或运行时组件。

06 · PRODUCTIZATION

从AI Native技术架构到可用产品：双方联合做了什么

Claudeforce没有创造另一套AI Native基础架构。它展示的是一套企业AI Native产品化参考架构：把已有技术组件围绕用户任务组织成可部署、可使用、可治理的产品。

先分清：哪些是复用，哪些是Salesforce升级，哪些是联合产品化

07 · ADOPTION

Salesforce客户还需要做什么

产品消除了大量通用组装工作，但企业特有的数据、语义、流程和责任边界仍然属于客户。

数据准备保证客户、商机和活动记录完整、及时、正确关联
语义准备完善对象与字段描述，明确阶段、指标和权威口径
能力准备将复杂确定性流程封装为Flow、Apex或Custom MCP Tool
权限准备检查External Client App、OAuth、CRUD、FLS、Sharing与确认策略
运营准备用典型任务持续验证质量、采用率与业务结果
一个例子：要让Claude分析Pipeline Coverage，企业必须明确使用Amount还是自定义ACV字段、哪些阶段计入Pipeline、用户能查看哪些区域，以及分析后是否允许更新Stage或Close Date。模型无法用推理替企业创造尚未定义的业务口径。

自定义能力边界：任意自定义API不能被假定为会自动进入标准Headless 360的Salesforce operations。公开支持的扩展方式是建立Custom MCP Server，将Flow、Apex、REST API、Named Query或API Catalog端点发布为具有明确描述、输入输出Schema和权限要求的Custom MCP Tool。

三类团队必须持续负责

责任方持续运营的资产核心评价
业务产品负责人任务方法、Skill、输出标准、人工责任与成功指标任务是否真正完成并改善业务结果
Salesforce平台团队数据与元数据质量、业务语义、能力契约、权限和执行可靠性事实是否可信、行动是否符合平台治理
AI平台团队模型与运行环境、评估集、监控、失败分析和版本回归模型或产品升级后质量是否稳定

CIO决定是否规模化的三道门槛

任务成立

存在高频、完整、结果可衡量的业务任务，而不只是偶发查询。

基础可靠

Salesforce数据、业务语义、权限与确定性流程足以支撑可信结果。

组织可运营

能够持续维护Skills、能力契约、评估、监控和责任分工。

还要算完整任务成本：经济性不能只比较模型或API单价，还应纳入Token与延迟、Connector和能力契约维护、评估运营、人工复核、异常处理及组织变更成本，再与节省工时和业务结果改善比较。

08 · IMPLICATIONS

Salesforce给企业智能化带来的启示

最大的变化不是增加一个Claude入口，而是把企业应用从“固定UI中的功能”升级为“可以被AI发现、理解、组合和安全执行的企业能力”，再将这些能力产品化。

传统企业应用

数据、流程和操作封装在页面、菜单与按钮中，主要服务于人的逐步操作。

→

AI Native企业能力

同一套数据、语义、流程和治理可以通过MCP、API、Skills与体验工具进入不同Agent和AI界面。

不要把“增加聊天入口”当作智能化终点要进一步将页面背后的业务能力从固定UI中释放出来，供不同AI界面复用。
MCP是基础设施，任务完成才是产品标准连接成功不能替代任务方法、企业上下文、确认机制和连续体验。
同时建设任务方法与企业能力两类资产Skill回答“应该怎样做”，Tool或operation回答“系统能够执行什么”。
把企业上下文当作正式产品能力明确权威事实、元数据、业务语义、模型可见信息与服务端规则的边界。
大规模能力需要渐进式披露能力较多时应设计发现、描述和执行机制，而不是把所有API平铺成工具列表。
让AI进入既有治理体系身份、权限、核心规则和审计应尽量由系统记录强制执行，Prompt不能代替权限。
产品化覆盖安装到持续运营管理员部署、用户初始化、审批、失败恢复、版本回归和效果评价都属于产品。
用完整任务结果衡量价值除调用成功率外，还要观察任务完成、口径正确、人工返工和业务指标改善。

09 · BOUNDARIES

边界、最终结论与主要来源

公开资料可以确认

  • Salesforce in Claude是专用插件，包含37个Sales Skills及Salesforce、Slack Connector
  • Salesforce Connector公开端点指向Headless 360 MCP Server
  • Headless 360 MCP Server提供四个MCP工具并使用Salesforce operations
  • 每用户OAuth调用继承Salesforce原生权限
  • 默认在写入前向用户展示并请求批准

不能过度推断

  • 不能把AIforce画成每次请求经过的独立网关
  • 不能断言每次任务都严格执行Discover→Describe→Dispatch
  • 不能假定完整Org元数据会一次性发送给Claude
  • 不能把所有Salesforce Hosted MCP Servers都说成只有四个工具
  • 不能把自定义API写成自动进入标准operations集合
最终结论Claudeforce不是新的Agent基础范式，而是一套值得借鉴的企业AI Native产品化样板：让业务方法可以被复用，让企业上下文可以按任务获得，让企业能力拥有明确契约，让模型判断、人的责任和系统执行处于同一条可验证工作链中。
